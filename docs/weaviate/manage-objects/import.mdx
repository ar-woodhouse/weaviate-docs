[Batch imports](../tutorials/import.mdx) are an efficient way to add multiple data objects and cross-references. For most use cases, we recommend **server-side batching** as the starting point: the server tells the client how much data to send next, so you don't have to tune batch parameters yourself. When you need manual control over the batch size and concurrency, or you are using a client that does not yet support server-side batching, use [manual batching](#manual-batching) instead.

## Server-side batching

<SsbStatus/>

With [server-side batch imports](../concepts/data-import.mdx#server-side-batching) (also called "automatic" batching), the client sends data in batch sizes determined by feedback from the server. This simplifies your code and helps the server manage its own load. Server-side batching offers two entry points:

- **Stream from a data source** (recommended for large datasets): Add objects to the import one at a time as you read them from the source, so the full dataset never has to fit in memory.
- **[Ingest an in-memory list](#ingest-an-in-memory-list)**: Import a list of objects that you already hold in memory with a single call.

Server-side batching uses the [gRPC API](../api/index.mdx), which current client versions enable by default.

### Ingest an in-memory list

If your objects are already in memory, you can import the whole list with a single call. ## Error handling

<!-- TODO[g-despot]: Add link to external Python references once created for "reference page" -->

Batch imports report failures per object: a problem with one object does not abort the rest of the import. Errors are reported the same way in server-side and manual batching. Inspect the failed items during and after the import to catch data issues early.

An object can appear in neither the failure list nor the successes, and its outcome is then unknown. [Reconcile the counts](../tutorials/import.mdx#large-dataset-strategies) when you need a resumable import.

<Tabs className="code" groupId="languages">
  <TabItem value="py" label="Python">

- Within a batching context manager, `batch.number_errors` holds a running count of failed objects and references. You can use this counter to stop the import process and investigate the failures.
- After the context closes, `collection.batch.failed_objects` and `collection.batch.failed_references` contain the failed items.
- The one-shot `data.ingest()` method returns the same result object as `insert_many`: its `errors` dict maps the original index of each failed object to its error.

Find out more about error handling on the Python client [reference page](/weaviate/client-libraries/python).

  </TabItem>
  <TabItem value="ts" label="JavaScript/TypeScript">

`data.ingest()` returns a result object. Inspect its `errors` field for the objects that failed to import.

  </TabItem>
  <TabItem value="gov5" label="Go (v5)">

Inspect the per-object errors on the result returned by the batcher.

  </TabItem>
  <TabItem value="java" label="Java">

Within a `batch.start()` streaming context, `batch.numberOfErrors()` reports the number of objects that could not be imported. The response returned by `insertMany` exposes the failed objects through its `errors()` method.

  </TabItem>
  <TabItem value="csharp" label="C#">

The response returned by `Batch.InsertMany` is a collection of per-object entries. Filter for entries where `Error` is not null to find the failed objects. With `Batch.StartBatch()`, each `Add` returns a handle whose result reports whether the object succeeded.

  </TabItem>
</Tabs>

## Stream data from large files

If your dataset does not fit in memory, do not load it all at once. Instead, read the source file lazily and add objects to the import as you go:

- With the [server-side streaming context](#server-side-batching), add each object as you read it from the file. The client sends data at the pace the server requests, so memory usage stays flat.
- In Python and TypeScript, the [one-shot import method](#server-side-batching) accepts any iterable, so you can pass a lazy source, such as a generator that reads the file record by record, instead of a fully loaded list.
- With manual batching, apply the same pattern: add objects to the batch as you read them.

For JSON files, use a streaming parser that yields one object at a time (such as `ijson` in Python). For CSV files, read the file in chunks (such as `pandas` with the `chunksize` parameter) rather than loading it whole.

## Additional considerations

Data imports can be resource intensive. Consider the following when you import large amounts of data.

### Asynchronous imports

[Asynchronous indexing](../concepts/indexing/vector-index.md#asynchronous-indexing) moves vector index construction off the write path, so an import does not wait for index building. To enable it, set the `ASYNC_INDEXING` environment variable to `true` and restart Weaviate. The setting is instance-wide: it applies to every collection, and to single-object writes and updates as well as batch imports. You cannot enable it for a bulk loader alone.

The trade-off is searchable-now. With asynchronous indexing on, the server can acknowledge a write before an indexing worker has added its vector, so a vector search can miss the object even though the import reported no failures. Reads that use the stored object and inverted index can still find it: get-by-ID, filtered object lists, keyword search and `over_all` totals, because those stores are written before the acknowledgement. That does not make every later query return it: a result set still depends on its filters, limits and ranking, and a replicated collection can answer from a replica that has not received the write. A vector aggregate counts only the objects that its vector search found, so it is not an object count.

Use asynchronous indexing when write throughput is the bottleneck and nothing queries the new data yet:

- A bulk load, backfill, or re-import into a collection that is not serving its new data, followed by a switch of the read path.
- A batch evaluation that indexes a dataset first and queries it afterwards.

Keep it off when a write must be searchable soon after it is acknowledged:

- One request writes an object and then searches for it.
- A user-facing "add and see it" flow.

If the setting is on and a later search must include the new writes, wait for the vector queue to drain before you query:

- `GET /v1/nodes?output=verbose` reports `vectorIndexingStatus` and `vectorQueueLength` for every shard on every node ([cluster node data](/deploy/configuration/status.md#cluster-node-data)).
- In Python, `collection.batch.wait_for_vector_indexing()` polls the shard status of the collection. It follows the shards of a batch import that ran in that collection's `batch` context manager (`stream()`, `dynamic()`, `fixed_size()` or `rate_limit()`), and returns when they report `READY`. After `data.ingest()` or `insert_many()` it can return before the vectors are indexed, because those paths do not record the imported shards for it.

Neither check is a barrier. Both describe the queue at one moment: writes that arrive afterwards are not covered, and neither check says what a query will rank in its top results. A query can also find a new object while its vector is still queued: a hybrid search can return it through its keyword part, and a filtered vector query can scan the filtered candidates directly instead of the graph. So a hit does not prove that indexing has finished. Readiness is a separate signal: `client.is_ready()` reports whether a node can serve traffic, not whether its vector index has caught up.

On a replicated collection, the read consistency level sets how many replica replies a read waits for and which object versions it can resolve. See [Consistency](../concepts/replication-architecture/consistency.md).

If you use Weaviate Cloud, check your cluster's default for this setting before you rely on either behaviour.
